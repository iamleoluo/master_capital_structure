# reference/ — 這個決策工具的推導與紀錄

**先讀 [00-purpose.md](00-purpose.md)。** 它說明這個系統是拿來做什麼的:
把 MSTR 的股價拆成幣、求償權、股數、情緒四件事,讓每一次決策可以指著
其中一件說「我是為了這個」。其餘文件都是在服務那個目的。

網站上看到的每一個數字背後都有一條推導。那些推導原本散在 `structure.ts`
的段落、`attribution.py` 的 docstring 與 commit message 裡,散著就等於沒有。
這個資料夾把它們收成一條線。

**這不是 API 文件,是思路文件。** 它回答「為什麼是這個形狀」,
不回答「這個函式怎麼呼叫」。

### ⚠️ 兩條軸,都叫「層」

- **[06](06-architecture.md) 的 `L1–L4`** 是**資料怎麼流**:採集 → 事件 → 操作 → 階段。
  程式模組 `archive` / `events` / `operations` / `phases` 與所有 commit 用的是這套。
- **[05](05-toolbox.md) 的分層**是**一把工具由什麼組成**:量 → 尺 → 工具 →
  組合 → 歸因 → 判斷 → 決策。它刻意**不用** `L` 編號。

兩條軸互相垂直。`L4` 只有一個意思,就是「階段」。

## 文件會腐爛,斷言不會

```bash
python3 reference/verify.py
```

01 與 02 裡每一條編號式子,在 `verify.py` 都有同號檢查,**對象是
`app/data/*.json`** —— 也就是前端實際拿到的那份資料,不是中間產物。
改了模型卻沒改文件,這支會紅。

容差不是隨便抓的,是從 JSON 的輸出位數推出來的上界(見檔案裡的註解)——
誤差超過上界就不是四捨五入,是模型真的錯了。

## 加東西進來的時候

- 新的恆等式 → 在 01 或 02 寫推導,**同時**在 `verify.py` 加同號檢查
- 換掉某個方法 → 在 04 記一條:症狀 / 原因 / 修正 / 教訓
- 資料來源、粒度或口徑變動 → 03,並確認資料品質頁的 finding 也跟著改
- 缺口變了 → 07(它是活的狀態,不要往裡面塞流水帳)
- 做完一步 → 08,**不要**在 05/06/07 再寫一份現況
- 改完跑 `python3 reference/build.py` 重新產生 HTML

引用具體數字時標上 as-of 日期。結構性的結論不標,因為它們不隨資料變動 ——
如果某個結論會隨資料變動,那它就不是結構性的,別寫成那樣。
