# 05 — 工具箱:代數怎麼變成可執行的宣告

⚠️ **這份文件的分層與 [06-architecture.md](06-architecture.md) 的 `L1–L4`
是兩條不同的軸,不要混淆。** 06 講**資料怎麼流**(採集 → 事件 → 操作 → 階段),
這裡講**一把工具由什麼組成**(量 → 尺 → 工具 → 組合 → 歸因 → 判斷 → 決策)。
本文刻意不用 `L` 編號 —— 那個編號只屬於 06。

進度在 [08-status.md](08-status.md) §2。

前面四份文件在說**模型是什麼**。這一份說**系統該怎麼長**。

論點只有一句:**一把資本操作應該是一個物件,不是散在三個檔案裡的三段東西。**
把它收成一個物件之後,代數會從「註解」變成「會被測試打臉的宣告」,
而解釋過去與模擬未來會共用同一段程式碼。

實作在 `mstr_cebe/toolbox.py`,論述成不成立看 `tests/test_toolbox.py` 過不過(40 條)。

---

## 1. 現在的問題:一把工具是三個互不相干的東西

以「優先股折價回購」為例,它在程式碼裡是這樣存在的:

| 在哪 | 是什麼 | 內容 |
|---|---|---|
| `mstr_cebe/chronicle.py` | 代數(字串) | `\Delta E = \frac{F-c}{pS}\times 10^8` |
| `mstr_cebe/attribution.py` | 語意(dict) | `"buyback": {"dclaims": -discount}` |
| `web/build_data.py` | 取參數(散落) | `discount = sum(shares*100 - cost_m*1e6 ...)` |

**沒有任何機制強迫這三者一致。** 我可以把 LaTeX 改成別的式子而測試全綠,
也可以把 `dclaims` 的符號寫反而文件毫無反應。這正是
[04-decisions.md](04-decisions.md) 裡「十二個名字,三個概念」那個病,
只是降了一層,發生在操作上。

還有第四份:**前端又寫了一套**。`app/src/charts/leverage.ts` 裡有
`Basis`(就是狀態)、`commonBtc`/`breakEven`/`amplification`(就是那幾把尺)、
以及 `applyAtmAccretion`(就是 ATM 這把工具)—— 全部用 TypeScript 重寫一次。
這直接違反了 CLAUDE.md 第一條規則,而它之所以會發生,**是因為沒有一個
東西可以讓兩邊共用**。

## 2. 觀察:狀態早就在那裡了

這不是新設計,是把已經存在的結構講明白。

整個系統從頭到尾只在談一個東西:

$$x = (H,\,C,\,S) \quad\text{加上當下幣價}\ p$$

而**每一把資本操作都只是這個狀態的一個轉移**。ATM 增發把 $S$ 加上 $n$、
把 $C$ 減去 $nP$;折價回購把 $C$ 減去 $F-c$;買幣把 $H$ 加上 $c/p$、
$C$ 加上 $c$。沒有例外,也沒有哪一把工具需要知道別的東西。

一旦承認這點,設計就自己浮出來了:**工具 = 狀態轉移函數**,
其餘欄位都是對那個函數的描述或宣告。

---

## 3. 七層,每層只做一件事

```
決策   給定現況與一個候選動作,會發生什麼?      ← 正向
判斷   這個動作加分嗎?效益多少?
歸因   觀察到的歷史裡,每一把工具貢獻多少?      ← 反向
組合   工具串工具(型別上封閉)
工具   State → State
尺     State → 純量(B、E、m、A、p₀)
量     H、C、S、p
```

分層的判準是**依賴方向只能往下**。工具層不知道時間、不知道資料來源、
不知道自己會被誰呼叫 —— 這正是它能同時服務歸因(解釋過去)與決策
(模擬未來)的原因。

幾個刻意的決定:

**`State` 不帶日期。** 時間是歸因層的事。工具只回答「這個動作把狀態變成什麼樣」,
一旦讓它知道日期,就會有人想在裡面寫「2026 年之後改用另一種算法」。

**尺是純函數。** `cebe(s)`、`gross_bps(s)` 沒有歷史、沒有副作用。
所以歸因層可以把同一個狀態反覆重放而不必擔心污染。

**工具不動幣價。** `test_price_is_untouched_by_every_tool` 把這條釘住 ——
幣價是行情不是決策,這是四層拆解([01-model.md §8](01-model.md#8-但中間那一層不是公司))
成立的前提。哪天有人讓某把工具去動 `price`,那個拆解就默默失效了。

## 4. 工具長什麼樣

```python
@dataclass(frozen=True)
class Tool:
    id: str
    params: Tuple[str, ...]      # 吃哪些輸入:c / F / n / x / P / d
    apply: Callable[[State, Params], State]    # 唯一的真實語意
    accretive: Optional[Predicate]             # 加分條件;None = 結構上恆中性
    latex_b: str                 # 對 B 的代數
    latex_e: str                 # 對 E 的代數
```

實際的一把:

```python
BUYBACK_PREFERRED = Tool(
    id="buyback_preferred", label="折價回購求償權", params=("c", "F"),
    apply=lambda s, k: replace(s, claims=s.claims + k["c"] - k["F"]),
    accretive=lambda s, k: k["c"] < k["F"],
    latex_b=r"\Delta B = 0",
    latex_e=r"\Delta E = \frac{F - c}{p\,S}\times 10^{8} > 0 \quad (c < F)",
)
```

四件事現在**擠在同一個視野裡**:付多少、消滅多少面額、什麼時候加分、
代數長什麼樣。改其中一個而忘了另一個,眼睛就會看到。

## 5. 關鍵:代數變成可以被打臉的宣告

這是整個設計真正的收穫,值得單獨講。

`accretive` 是一個**宣告**:「這個動作在這些條件下讓 $E$ 上升」。
而 `apply` 是**事實**:套下去 $E$ 到底怎麼變。兩者可以互相驗證:

```python
claimed = tool.accretive(state, params)
actual  = effect(tool, state, **params)["dE"] > 0
assert claimed is actual
```

`test_every_tool_predicate_agrees_with_applying_it` 掃過所有工具與組合,
**門檻兩側各驗一次**。所以:

- 寫錯 `apply` 的符號 → 紅
- 寫錯 `accretive` 的不等號方向 → 紅
- 新增一把工具卻忘了同步謂詞 → 紅

更進一步,連 LaTeX 都能驗。`test_atm_closed_form_threshold_equals_predicate`
把 `latex_e` 宣告的封閉式子 $\frac{P}{p}\times 10^8 > E$ 真的算一次,
跟謂詞 $m > 1$ 比對 —— 兩種寫法必須等價。
`test_effect_matches_closed_form_for_buyback` 同理。

**代數不再是寫在旁邊的說明,而是系統的一部分。**

## 6. 組合在型別上封閉

真實世界的動作幾乎都是組合 —— 錢要先從某處來,才能往某處去。

```python
ATM_TO_BUYBACK = compose(
    id="atm_to_buyback", params=("n", "P", "d"),
    steps=(
        Step(COMMON_ATM,        lambda s, k: {"n": k["n"], "P": k["P"]}),
        Step(BUYBACK_PREFERRED, lambda s, k: {"c": k["n"] * k["P"],
                                              "F": k["n"] * k["P"] / (1 - k["d"])}),
    ),
    accretive=lambda s, k: mnav(s, k["P"]) > 1 - k["d"],
)
```

兩個設計點:

**`compose()` 回傳的還是 `Tool`。** 所以組合可以再被組進另一個組合
(`test_combos_are_closed_under_composition` 釘住這件事),而且歸因、判斷、決策三層
完全不需要知道自己拿到的是單一工具還是組合。

**`wire` 收得到當下的狀態,不只是參數。** 賣幣換到多少現金要看幣價,
而且第二步看到的應該是第一步之後的狀態。這讓「賣幣 → 回購」能誠實地
把兩步串起來,而不是硬塞一個預先算好的數字。

組合的 `accretive` 也一樣要被驗:`m > 1 - d` 這個門檻在
$d \in \{0, 0.10, 0.27\}$ 三個折價率、每個門檻兩側各測一次。
$d = 0$ 時它必須退化成純 ATM 的 $m > 1$ —— 這條測試順便證明了組合的
代數與單一工具的代數是連續的。

## 7. 同一個 `apply`,同時服務過去與未來

現在的系統有兩套操作語意:

| | 在哪 | 做什麼 |
|---|---|---|
| 反向 | `attribution.build_operations()`(Python) | 從歷史資金流算各操作貢獻 |
| 正向 | `charts/leverage.ts` 的 `runScenario()`(TypeScript) | 模擬「若幣價到 X、增發 Y%」 |

**兩邊描述的是同一批動作,卻是兩份獨立的程式碼,而且跨語言。**
改了其中一邊,另一邊不會有任何反應。

在 Tool 的設計下,這兩件事是同一個函數的兩種用法:

```
歸因  = 對「已經發生的」工具序列做 Shapley
模擬  = 對「假設要做的」工具序列 apply 一次
```

這正是這個工具作為**決策工具**最需要的性質 ——
「上一季那筆增發做得好不好」與「現在這筆增發該不該做」
必須用同一把尺回答,否則兩個答案沒有可比性。

`test_log_decomposition_of_a_sequence_telescopes` 展示了這件事:
把一串操作依序套用,各步的 $\Delta \ln E$ 相加精確等於總變化 ——
這就是逐日鏈結在做的事,只是把「天」換成「操作」。**同一個機制。**

## 8. 效益怎麼算:三個層次的答案

「這個決策對不對」不是一個問題,是三個,而且要分開回答。

### 層次一:方向 —— 兩把尺各自怎麼動

```python
effect(BUYBACK_PREFERRED, state, c=0.73e9, F=1e9)
# → {"dB": 0.0, "dE": +751.3}
```

兩欄並排看。不一致的地方就是這家公司最常被誤讀的地方 ——
折價回購對 $E$ 是實打實的加分,對 $B$ 是**結構上的零**。

### 層次二:判斷 —— 加分的條件是什麼

不是「這次加分了」,而是「在什麼條件下加分」。`accretive` 就是那個條件,
而且它是可執行的,不是一句話。

### 層次三:效率 —— 每一塊錢換到多少

前兩層都只說了正負,沒說**划不划算**。決策要比較的是這個:

$$\text{效率} = \frac{\Delta E}{\;c \big/ (p\,S) \times 10^{8}\;}$$

分母是「投入的美元換算成每股的聰」,所以結果是無單位的報酬率。
折價回購的封閉解特別乾淨:

$$\text{效率} = \frac{F-c}{c} = \frac{d}{1-d}$$

| 折價 $d$ | 資本報酬率 |
|---|---|
| 4.1%(實際 STRC 均價 \$95.87) | 4.3% |
| 10% | 11.1% |
| 27%(壓力最大時的市價) | **37.0%** |
| 40% | 66.7% |

對照:**同一塊錢拿去買幣,報酬率是 0**(`test_buying_btc_has_zero_capital_efficiency`)。

這張表就是「折價回收」那段期間的決策依據 ——
不是「回購比較好」這種感覺,是 37% 對 0%。

## 9. 這個設計刻意不做的事

**不做通用 DSL。** 工具就是那幾把,加一把是加一筆資料。做成可設定的
表達式引擎會讓「新增工具」看起來很便宜,實際上把錯誤從編譯期推到執行期。

**不把資料抽取放進 `apply`。** 8-K 的版型換過四次(見
[03-data.md](03-data.md#3-8-k-的版型換過四次),而折價回購的代數一次都沒變過。
變動頻率差這麼多的兩件事不該綁在一起。

**不讓工具知道時間。** 一旦可以,就會有人寫「某個日期之後改用另一種算法」,
然後歷史重算就再也對不起來。

**不追求「涵蓋所有可能的資本操作」。** 只放**這家公司真的用過、
或有授權但刻意不用**的。後者本身就是訊號 —— 普通股回購授權掛著不動用,
是因為 $m > 1$ 時它會毀滅價值,而那個判斷現在是一行可執行的謂詞。
